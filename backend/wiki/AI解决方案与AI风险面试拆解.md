# EchoMind：AI 解决方案与 AI 风险岗位面试拆解

## 1. 阅读说明与证据纪律

这份材料的目标不是逐行背代码，而是帮助面试时讲清楚：为什么做、服务谁、如何解决问题、系统怎样运行、哪里可能出错、怎样量化优化。

证据分为四类：

- **代码事实**：源码中已经实现并可定位的行为。
- **运行事实**：本次环境中已经验证的行为，例如 `/health`、`/chat`、知识库统计接口。
- **文档描述**：PDF 和 wiki 对设计目标、面试口径的说明；不自动等于生产结果。
- **待验证项**：需要通过真实测试集、日志或压测确认的结论。

特别注意：PDF 中出现的准确率、召回率或“企业级”等表述，除非有可复现评测报告支持，否则面试时应说成“设计目标/评测框架支持”，不要说成已达成的生产指标。

## 2. 一句话定位

EchoMind 是一个面向企业客服场景的、路由驱动的多 Agent 客服运行时：它先理解用户问题，再决定是否检索知识、由哪个专业角色处理、是否需要协同或转人工，最后输出回复并记录运行数据。

它的核心价值不是“把问题交给大模型”，而是把大模型放进一个可路由、可约束、可降级、可评测的业务流程中。

## 3. 需求来源、服务对象与问题定义

### 3.1 需求来源

从项目文档能确认的是：需求来自企业客服中常见的复杂请求，而不是来自某个已被代码证明的特定客户。典型问题包括退款、发票、重复扣款、物流、登录失败、错误码、投诉和转人工。

面试时建议表述为：

> 需求来源于企业客服运营中的三类压力：问题分流不准、上下文容易丢失、系统上线后难以持续评估和优化。

不要虚构具体客户、订单系统或上线规模。

### 3.2 购买者与使用者

- **购买者/决策者**：企业的客服负责人、客户体验负责人、IT/数字化负责人，或需要降本增效的业务部门。
- **直接使用者**：企业最终客户，以及企业内部客服/运营人员。
- **系统维护者**：研发、AI 应用工程师、知识库运营和风险/质量人员。

当前页面主要展示最终客户的聊天入口；监控、评测、Trace 和知识库管理更适合内部运营或开发者视角，不应全部暴露给普通客户。

### 3.3 解决的问题

| 业务问题 | 系统机制 | 结果目标 |
|---|---|---|
| 技术问题被普通客服回答 | 细粒度意图识别 + 技术角色路由 | 提高专业匹配度 |
| 退款问题回答不谨慎 | 账单角色 + 知识库 + 处理规范 | 减少错误承诺和资金风险 |
| 复合问题只回答一半 | 主 Agent + 辅助 Agent 并行协作 | 降低漏答 |
| 多轮对话忘记上下文 | Redis 工作记忆 + ChromaDB 长期记忆 | 保持连续性 |
| 知识更新后需要改代码 | Skills 目录动态加载 | 降低规则迭代成本 |
| 线上效果只能靠感觉 | Monitor + Evaluator + 回归基线 | 支持可量化优化 |

## 4. 整体架构与数据流

```text
用户消息
  ↓
FastAPI /chat
  ↓
读取 Redis 当前会话记忆
读取 ChromaDB 情景记忆和用户画像
  ↓
IntentRecognizer：LLM + 本地字符 n-gram 相似度 + 关键词规则
  ↓
得到 intent / group / confidence / entities / urgency
  ↓
判断是否需要知识检索
  ↓
MCPToolManager：查询改写 → 并行召回 → 去重 → LLM 重排 → Top-K
  ↓
AgentOrchestrator：主 Agent、辅助 Agent、性能路由、升级判断
  ↓
角色 Prompt + Skills + 记忆 + 知识片段 + 实体
  ↓
LLM 生成回复，必要时调用角色白名单工具
  ↓
写回 Redis；异步更新用户画像/情景记忆
  ↓
返回客服回复；Monitor 记录运行指标
```

独立评测链路为：

```text
评测集 → /eval/run → 意图识别评测
                 → 真实调用编排器生成回复
                 → LLM-as-Judge 四维评分
                 → 与历史基线比较 → 回归提示和优化建议
```

## 5. 技术栈为什么这样选

| 技术 | 在项目中的职责 | 解决的问题 | 选型取舍 |
|---|---|---|---|
| Python | AI 编排、检索、评测和服务实现 | 便于连接 LLM、向量库和异步 I/O | 研发效率高；强类型和工程治理需要额外补充 |
| FastAPI | HTTP API、Swagger、异步入口 | 对外提供 `/chat`、知识库、监控和评测接口 | 适合异步服务；生产上仍需鉴权、限流和网关治理 |
| Anthropic SDK | 意图识别、回复生成、查询改写、重排、Judge | 复用大模型能力 | 延迟、成本、供应商可用性是主要风险 |
| Redis | 当前会话工作记忆、摘要和 TTL | 低延迟读写短期上下文 | 适合短期状态；不适合承担完整长期知识 |
| ChromaDB | 知识库、情景记忆、用户画像 | 语义检索和持久化向量数据 | 适合 Demo/中小规模；大规模生产需评估高可用与索引能力 |
| Prometheus | 指标采集 | 观察延迟、成功率、工具状态 | 只负责指标，不等于完整日志/Trace 系统 |
| Nginx | 反向代理和统一入口 | 隔离前端与后端、统一端口 | 生产还应配合 TLS、鉴权和限流 |
| Docker Compose | 编排 API、Redis、ChromaDB、Prometheus、Nginx | 本地一键复现多服务依赖 | 简单易用；不等同于生产级集群编排 |

## 6. 核心模块：处理逻辑、设计原因、风险与降级

### 6.1 FastAPI 入口层

**过程**：校验 `message/user_id/conv_id`，读取上下文，调用编排器，写回记忆，返回结构化响应。

**为什么这样设计**：把 HTTP 协议和 AI 编排解耦；Pydantic 保证输入输出结构稳定；异步接口适合等待模型和外部存储。

**降级/风险**：服务未初始化返回 503；但当前 `allow_origins=["*"]`、没有用户认证和请求限流，属于明确的生产风险。应增加身份认证、租户隔离、敏感字段脱敏、超时和请求大小限制。

### 6.2 意图识别

**过程**：LLM 语义判断、模板相似度、关键词规则并行执行，再按权重投票；代码默认 LLM 0.7、向量 0.2、规则 0.1。还会提取订单号、金额、日期和错误码。

**为什么这样设计**：只用关键词覆盖不足，只用 LLM 成本高、延迟和行为不稳定；融合让语义能力与确定性兜底互补。

**真实实现边界**：当前没有可靠的外部 Embedding 服务时，会退化为本地字符 1-3 gram 哈希向量。这不是严格意义上的语义 Embedding，面试时必须准确说明。

**降级**：LLM 失败时优先使用向量或关键词；融合分数低于阈值时归为 `other`。风险是规则重叠、类别不平衡和复合问题被压成单一主意图。

### 6.3 Agent 编排与角色隔离

**角色**：General 负责通用咨询和兜底；Technical 负责登录、报错和故障排查；Billing 负责退款、扣款和发票；Escalation 负责转人工。

**过程**：根据意图、关键词、实体、紧急程度和 Agent 运行表现生成 `RoutingDecision`；明确复合问题时选择主/辅 Agent 并行执行；专属 Agent 失败时尝试 GeneralAgent。

**为什么这样设计**：技术、账单、通用问题的回答原则不同。当前三个 Agent 底层仍共享同一个 LLM 客户端，主要差异是角色契约、Prompt、工具范围和统计维度；因此它是轻量的多角色编排，而不是三个完全独立的模型系统。

**风险与优化**：主辅阈值可能误触发，导致成本和延迟上升；并行结果合并可能重复或矛盾。应增加路由混淆矩阵、复合问题专门测试集、最大并行数、总预算和冲突合并规则。

### 6.4 知识库与 RAG

**过程**：文档按约 500 字切片，ChromaDB 在写入和查询时负责向量化；MCP 工具管理器对查询进行改写，并行召回、内容去重、LLM 重排，最后取 Top-K 注入 Agent 上下文。`/chat` 默认取前 3 条、每条截断约 600 字。

**为什么这样设计**：Embedding 负责大规模粗召回，重排负责从候选中选出更适合回答的问题；全部内容直接塞给生成模型会增加 token、延迟和噪声。

**重要边界**：知识库文档不会转换成意图。意图识别模板向量和 RAG 文档向量是两条不同链路。

**降级**：查询改写失败使用原始问题；重排失败保留原始顺序；工具超时、异常或熔断时使用 fallback，主对话可继续生成不带知识库的回答。对于退款、账户安全等高风险问题，仅“无知识回答”并不一定安全，生产上应改为谨慎拒答或转人工。

### 6.5 Skills

**过程**：启动扫描 `skills/` 下的 Markdown/JSON/TXT，根据 Agent 类型和关键词动态注入规则；支持 `/skills/reload` 热加载。

**职责边界**：知识库回答“业务事实是什么”；Skill 约束“客服应该怎么处理”。例如先收集错误码、退款不能承诺立即到账、不要索要密码验证码。

**风险**：规则冲突、注入过多导致回复变长、关键词覆盖不足、规则与知识库事实过期。优化方向是版本管理、优先级、冲突检测、审批发布和基于评测集的回归。

### 6.6 记忆

**三层**：Redis 保存当前会话最近消息；ChromaDB `episodic` 保存历史摘要；ChromaDB `user_profile` 保存用户画像。

**过程**：先读短期和相关长期记忆，生成回复后写回消息；消息过多时调用 LLM 压缩旧消息，Redis 保留近期内容，摘要进入长期存储；画像更新异步执行，不阻塞当前响应。

**为什么这样设计**：短期记忆追求低延迟，长期记忆追求跨会话召回，画像追求结构化沉淀；把三种数据混在一个存储中会导致成本、检索噪声和生命周期难以控制。

**风险/降级**：Redis 或 ChromaDB 不可用时应进入无记忆模式；历史记忆只能作为辅助，不能覆盖当前问题和权威业务政策。生产必须考虑租户隔离、删除权、PII 脱敏、画像错误传播和 TTL 策略。

### 6.7 工具可靠性治理

工具调用包含 JSON Schema 参数校验、TTL 缓存、超时、三态熔断器、fallback、成功率/延迟统计。

这解决的是“工具不是永远可用”的工程问题：参数错误不应进入下游；连续失败不应造成雪崩；重复查询不应反复消耗模型和数据库；单个依赖故障不应拖垮整条客服链路。

需要补充的生产能力：幂等键、重试退避、外部调用预算、敏感操作二次确认、审计日志、工具权限按租户隔离。

### 6.8 Monitor 与评测

Monitor 采集 Agent/工具调用次数、成功率、平均延迟、连续失败、熔断状态，并可生成告警和路由惩罚项。Evaluator 负责离线意图指标、端到端回复质量、回归检测和建议。

注意：Monitor 是在线健康度；Evaluator 是离线/准离线质量。二者不能互相替代。

## 7. 评测集与量化指标方案

### 7.1 测试集怎么建立

建议先做 300-500 条，而不是直接声称已有 500 条：

1. 按业务意图分层：退款、发票、支付、订单、物流、登录、崩溃、账户安全、投诉、转人工、问候、其他。
2. 每类包含标准表达、口语表达、错别字、混合中英文、缺少关键实体和对抗性表达。
3. 单独建立复合问题集，例如“登录报错且重复扣款”。
4. 单独建立多轮集，测试订单号、金额、错误码在后续轮次是否被保留。
5. 用 AI 生成候选，再由人工审核；测试集和调参样本必须分离。
6. 固定 train/dev/test 或 prompt-tuning/dev/holdout，避免反复调到测试集上造成泄漏。

### 7.2 意图识别指标

代码已实现：

- Accuracy = 正确预测数 / 总样本数
- 每类 Precision = TP / (TP + FP)
- 每类 Recall = TP / (TP + FN)
- 每类 F1 = 2PR / (P + R)
- Macro-F1 = 各类别 F1 的平均值

建议重点看 Macro-F1 和每类 Recall，而不是只看 Accuracy。客服中“转人工”“账户安全”“退款”等高风险类漏检代价不同，应增加加权风险指标：

```text
Risk-weighted error = Σ(错误类型成本 × 错误次数) / 总样本数
```

还应报告混淆矩阵、低置信度比例、规则/LLM/向量分支的一致率和缓存命中率。

### 7.3 RAG 召回与排序指标

必须给每个问题标注一个或多个“相关文档 chunk”，再计算：

- Recall@K：相关 chunk 是否出现在前 K 个结果中。
- Precision@K：前 K 个结果中有多少是相关的。
- Hit@K：至少命中一个相关 chunk 的问题比例。
- MRR：第一个相关结果排名越靠前得分越高。
- nDCG@K：适合多个相关文档且相关性有等级的场景。

Embedding 粗召回和 Rerank 精排要分别评测：如果粗召回 Recall@50 很低，不能把问题归咎于 Rerank；如果 Recall@50 高但 nDCG@3 低，说明排序有问题。

### 7.4 生成质量指标

现有代码用 LLM-as-Judge 评价相关性、准确性、完整性、有用性，综合分是四项平均值。它适合规模化筛查，但不能单独作为事实正确性的最终依据，因为 Judge 也会偏差。

建议增加：

- 业务事实准确率：与人工/规则核验的关键事实是否一致。
- 引用/依据覆盖率：回答中的政策事实是否能在召回文档中找到。
- 无依据断言率：没有证据却给出确定承诺的比例。
- 必填字段收集率：退款、技术排障是否收集了必要信息。
- 安全违规率：是否索要密码、验证码，是否越权承诺或泄露信息。
- 转人工准确率：该升级时升级、不该升级时不过度升级。
- 多轮任务完成率：完整对话是否最终解决目标。

### 7.5 性能与可靠性指标

- p50/p95/p99 端到端延迟，而非只看平均延迟。
- 首次响应时间、LLM 调用次数、每请求 token 和成本。
- Agent 成功率、工具成功率、熔断次数、fallback 比例。
- Redis/ChromaDB 依赖失败率。
- 并发下错误率、超时率和队列等待时间。
- 线上 bad case 率、人工转接率、重复咨询率。

## 8. AI 风险岗位需要主动讲的风险

1. **事实幻觉**：知识库为空、检索错或政策过期时，模型可能编造规则。高风险领域应要求有依据回答，证据不足则澄清或转人工。
2. **路由错误**：退款分到技术 Agent 会造成业务错误；账户安全漏检可能造成严重后果。
3. **Prompt/Skill 注入**：文档或用户输入可能诱导模型绕过规则；应分离不可信内容、限制工具权限并做输出校验。
4. **隐私风险**：用户 ID、订单号、金额、画像进入日志/向量库，需要脱敏、访问控制、留存期限和删除机制。
5. **越权工具调用**：角色白名单是基础，还要做参数校验、审批、审计和幂等。
6. **评测偏差**：AI 生成测试集可能覆盖不足；LLM Judge 可能偏爱流畅但错误的答案，必须用人工抽检校准。
7. **供应商依赖**：模型不可用会影响意图、改写、重排和回复多个环节；应设置超时、fallback、模型切换和成本预算。
8. **可解释性不足**：应保留 request_id、意图、路由、召回、工具和降级原因，但这些信息主要给内部运营，不必展示给普通客服用户。

## 9. 最值得优化的顺序

1. 先建立标注评测集和人工抽检闭环，确认问题到底在意图、召回、排序还是生成。
2. 将“知识库不可用时继续回答”改成按风险分级：低风险可降级，高风险必须谨慎回答或转人工。
3. 把本地字符哈希向量明确定位为兜底，并用真实 Embedding 做离线对比。
4. 为 RAG 加 chunk 元数据、版本、来源、有效期和权限过滤。
5. 增加结构化 Trace，但只放在内部运营界面；普通用户只看客服回复和必要的处理状态。
6. 将平均延迟改成 p95/p99，并拆分意图、改写、召回、重排、生成各阶段耗时。
7. 增加认证、租户隔离、PII 脱敏、审计日志、限流和工具权限治理。
8. 评测通过后再优化并行 Agent 和模型调用次数，避免没有基线就盲目复杂化。

## 10. 面试时的最终回答模板

> 这个项目的需求来自企业客服里大量跨领域、带上下文和业务规则约束的问题。它服务的最终对象是企业客户，但系统使用者既包括企业的终端消费者，也包括内部客服和运营人员。我的设计不是把所有请求直接交给一个大模型，而是先用意图识别完成结构化理解，再由编排器决定专业角色、知识检索、工具权限和是否协作。知识库负责提供事实，Skills 负责处理规范，Redis 和 ChromaDB 分别承担短期、长期记忆，工具层提供超时、缓存、熔断和降级。最后通过监控观察线上健康度，通过标注评测集评估意图 Accuracy/Macro-F1、RAG Recall@K/Precision@K、回答准确性和安全违规率。这样系统才从“能聊天”变成“可控制、可解释、可持续优化”的客服应用。
